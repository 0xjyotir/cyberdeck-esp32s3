01

Wi-Fi · 802.11

Six ways to read 2.4 GHz Wi-Fi airspace, from a polite active scan to raw promiscuous capture and frame injection on hardware you own.

1.1 Active Wi-Fi scan +

Runs a standard active Wi-Fi scan: the ESP32 briefly tunes every 2.4 GHz channel and records every access point that answers a probe. It repeats every couple of seconds while the module is running, so the telemetry table keeps refreshing with whatever is in range.

What the output means

ssid
The network's broadcast name. Shows Hidden when the AP cloaks its SSID.
bssid
The access point's MAC address — a unique per-radio hardware ID, even when two APs share one SSID.
ch
The 2.4 GHz channel (1–13) the AP is broadcasting on.
rssi
Received signal strength in dBm. It is always negative; closer to 0 is stronger (e.g. −45 is right next to you, −85 is far or through walls).

Example telemetry

{"module":"1.1","status":"ok","data":{"ssid":"HomeNet_5G","bssid":"A4:2B:8C:1D:7E:F0","ch":6,"rssi":-52}}
View this module’s .ino source →
1.2 Wardriving logger +

A continuous channel-monitor sweep meant to run while you walk or drive. It logs the same access-point attributes as the scanner, but is built to keep streaming so you can map which networks appear and drop out as you move.

What the output means

ssid
Network name of each AP seen on the sweep.
bssid
The AP's MAC address — the stable key you'd use to tell two APs apart in a log.
ch
Channel the AP was heard on.
rssi
Signal strength in dBm at the moment of capture; watching it rise and fall is how you tell you're getting closer to or further from a transmitter.

Example telemetry

{"module":"1.2","status":"ok","data":{"ssid":"CafeGuest","bssid":"DC:A6:32:04:11:9B","ch":11,"rssi":-67}}
View this module’s .ino source →
1.3 Promiscuous sniffer +

Puts the Wi-Fi radio into promiscuous (monitor) mode and hops channels, capturing raw 802.11 management frames — including the probe requests that phones and laptops broadcast while looking for known networks. This is passive: it only listens.

What the output means

ssid
Network name pulled from a captured frame, where one is present.
bssid
The source MAC address in the raw frame — for a probe request this is the client device, not an AP.
ch
The channel the sniffer was parked on when it caught the frame.
rssi
Signal strength in dBm of the captured frame, i.e. how close the transmitting device is.

Example telemetry

{"module":"1.3","status":"ok","data":{"ssid":"","bssid":"3C:22:FB:8A:55:10","ch":1,"rssi":-71}}
View this module’s .ino source →
1.4 Network / client discovery +

A detailed attribute sweep of the local wireless infrastructure. Where the basic scan just lists APs, this profiles each one — including its authentication/encryption type — so you can see at a glance which networks are open and which are secured.

What the output means

ssid
Network name (or Hidden for a cloaked network).
bssid
The access point's MAC address.
ch
Operating channel of the AP.
rssi
Signal strength in dBm. (The standalone sketch also prints the auth mode — OPEN / WEP / WPA-PSK / WPA2-PSK / WPA3-PSK — alongside each entry in its serial log.)

Example telemetry

{"module":"1.4","status":"ok","data":{"ssid":"Office-WPA2","bssid":"F0:9F:C2:3D:6A:88","ch":4,"rssi":-58}}
View this module’s .ino source →
1.5 AP hosting +

Turns the deck into its own access point (Cyberdeck_AP) and then reports the stations that connect to it. Useful as a controlled target you own — you can watch devices associate and read their link quality.

What the output means

ssid
Carries the soft-AP's own gateway IP address once the access point is up (e.g. the address you'd point a browser at). The standalone sketch additionally lists each connected station's MAC and RSSI.

Example telemetry

{"module":"1.5","status":"ok","data":{"ssid":"192.168.4.1","bssid":"-","ch":1,"rssi":0}}
View this module’s .ino source →
1.6 Frame lab / injection test +

A lab bench for 802.11 frame injection: it transmits a hand-built test beacon frame on channel 1 and reports whether the transmit call succeeded. It's a capability check for the radio's injection path on a network you control — not a tool pointed at other people's devices.

What the output means

ssid
Carries the transmit status string for each injected frame — i.e. confirmation that the test frame was broadcast on channel 1.

Example telemetry

02

Bluetooth LE

Discover, fingerprint and interrogate BLE peripherals — advertisement sniffing, full GATT enumeration, live value reads and a connection stress test.

2.1 BLE scan & fingerprint +

An active BLE scan that discovers nearby Bluetooth Low Energy peripherals and fingerprints each one — the advertised name, its address and how strong the signal is. This is how you build a picture of what BLE devices are around you.

What the output means

name
The device's advertised friendly name, or <Unnamed> if it doesn't broadcast one.
addr
The BLE device address (MAC-style, six hex bytes) — the identifier you use to target a specific device later.
rssi
Signal strength in dBm; closer to 0 means the device is nearer.
uuid
Any service UUID the device advertises, which hints at what it is (e.g. a heart-rate or battery service).

Example telemetry

{"module":"2.1","status":"ok","data":{"name":"Mi Band 7","addr":"c4:9d: a1:22:0b:7e","rssi":-61,"uuid":"0000fee0-0000-1000-8000-00805f9b34fb"}}
View this module’s .ino source →
2.2 GATT service enumeration +

Connects to a BLE peripheral and walks its GATT table, listing every service and characteristic it exposes along with their read/write permission flags. This is the map of what a device lets you talk to.

What the output means

name
The connected peripheral's name.
uuid
The UUID of each service / characteristic found — the address of a specific data point inside the device.
rssi
Link signal strength in dBm during enumeration.
payload
Carries the permission flags for the characteristic — whether it can be read and/or written (e.g. READ vs LOCKED).

Example telemetry

{"module":"2.2","status":"ok","data":{"name":"Thermostat","uuid":"00002a6e-0000-1000-8000-00805f9b34fb","rssi":-55,"payload":"READ"}}
View this module’s .ino source →
2.3 Advertisement sniffer +

A passive sniffer that captures the raw advertisement packets BLE devices continuously broadcast, dumping the payload bytes as hex. Nothing is connected to — it only listens to what's already in the air.

What the output means

name
Advertised name if present.
addr
The broadcasting device's address.
rssi
Signal strength in dBm of the captured advertisement.
payload
The raw advertisement payload as a hex string (or None if the packet carried no payload) — this is the unparsed manufacturer/service data the device is broadcasting.

Example telemetry

{"module":"2.3","status":"ok","data":{"name":"","addr":"7a:11:3e:9c:04:df","rssi":-74,"payload":"0201061AFF4C000215..."}}
View this module’s .ino source →
2.4 Custom beacon broadcaster +

Broadcasts a custom BLE beacon from the deck so you can verify range and that a scanner (your phone, another deck) picks it up. It's a transmit-side test — the deck is the thing being discovered.

What the output means

name
The beacon name the deck is advertising (e.g. Cyberdeck-Spam).
uuid
The service UUID baked into the broadcast beacon.
rssi
Reported signal context for the broadcast.
payload
The beacon payload being advertised.

Example telemetry

{"module":"2.4","status":"ok","data":{"name":"Cyberdeck-Spam","uuid":"12345678-0000-1000-8000-00805f9b34fb","rssi":0,"payload":"active"}}
View this module’s .ino source →
2.5 GATT exploration + value read +

Goes a step beyond enumeration: it connects to a peripheral, finds every readable characteristic and actually reads back its live value, dumping it as hex. This is how you pull the current data a device is holding.

What the output means

name
The connected device's name.
uuid
The UUID of the characteristic that was read.
payload
The live value of that characteristic as a hex string — the actual bytes stored on the device at read time (decode per the characteristic's spec to get a temperature, battery %, etc.).

Example telemetry

{"module":"2.5","status":"ok","data":{"name":"BatterySvc","uuid":"00002a19-0000-1000-8000-00805f9b34fb","payload":"64"}}
View this module’s .ino source →
2.6 Device connection stress test +

Repeatedly connects to and disconnects from a target peripheral and times each handshake, so you can measure how reliably and how fast a device accepts connections. Each attempt reports success or failure plus its latency.

What the output means

name
The target device being tested (addr is also reported).
uuid
Service context for the target.
rssi
Link signal strength during the test.
payload
Carries the per-attempt result — the connection latency in milliseconds on success, or a FAILED marker when a handshake doesn't complete.

Example telemetry

{"module":"2.6","status":"ok","data":{"name":"Target","uuid":"-","rssi":-60,"payload":"attempt 1: SUCCESS 212 ms"}}

04

2.4 GHz · nRF24

Survey the raw 2.4 GHz ISM band with an nRF24L01+ — spectrum energy, packet capture, address discovery and a lab transmitter for your own link tests. (Hardware-untested.)

4.1 Spectrum scan +

Sweeps all 126 nRF24 channels across 2400–2525 MHz and samples how much carrier energy sits on each one (32 samples per channel per pass). On the dashboard this feeds the live spectrum graph — tall bars are busy frequencies (Wi-Fi, Bluetooth, other 2.4 GHz gear). It also doubles as the nRF24 wiring check: if the module isn't found you get nrf_not_found.

What the output means

ch
The nRF24 channel number (0–125).
mhz
That channel's frequency in MHz (2400 + channel).
level
Energy reading for the channel on this pass, 0–32. Higher means more activity / a stronger carrier was detected on that frequency.

Example telemetry

{"module":"4.1","status":"ok","data":{"ch":76,"mhz":2476,"level":18}}
View this module’s .ino source →
4.2 Packet sniffer +

Listens on the default pipe while hopping channels 0–83 and dumps any nRF24 payloads it catches as raw hex. This is the capture tool for seeing the actual bytes small 2.4 GHz devices (toys, some wireless peripherals) are sending.

What the output means

ch
The channel the packet was captured on.
addr
The pipe address the packet arrived on.
len
Payload length in bytes.
payload
The captured packet bytes as a hex string.

Example telemetry

{"module":"4.2","status":"ok","data":{"ch":42,"addr":"0xE7E7E7E7E7","len":8,"payload":"A1B2C3D4E5F60718"}}
View this module’s .ino source →
4.3 Address discovery +

Sniffs for the short preamble that precedes nRF24 packets and, by hopping the band, reports candidate pipe addresses it keeps seeing. It's how you find the address a device is using before you can sniff its packets in full.

What the output means

ch
Channel where the candidate address was observed.
addr
A candidate nRF24 pipe address recovered from the preamble sniff.
hits
How many times that address was seen — more hits means a more confident, real address rather than noise.

Example telemetry

{"module":"4.3","status":"ok","data":{"ch":17,"addr":"0xC2C2C2","hits":5}}
View this module’s .ino source →
4.4 Protocol analysis +

Captures packets and, per packet, reports the length and data rate and makes a heuristic guess at whether it looks like control traffic or data traffic — a first-pass characterisation of an unknown 2.4 GHz link.

What the output means

ch
Channel of the analysed packet.
addr
Pipe address the packet came from.
len
Payload length in bytes.
rate
The nRF24 data rate the link is using (e.g. 1 Mbps / 2 Mbps / 250 kbps).
guess
A heuristic classification of the traffic — e.g. a short, regular packet reads as control, a longer one as data.

Example telemetry

{"module":"4.4","status":"ok","data":{"ch":33,"addr":"0xE7E7E7E7E7","len":4,"rate":"1Mbps","guess":"control"}}
View this module’s .ino source →
4.5 Packet storage +

Buffers captured packets into an in-RAM ring buffer (32 frames) and keeps a running count, so you can grab a burst of traffic and review the most recent frames rather than watching them scroll past once.

What the output means

stored
How many frames are currently held in the ring buffer (caps at 32, oldest dropped first).
last_addr
The pipe address of the most recently stored packet.
last
The payload of the most recently stored packet.

Example telemetry

{"module":"4.5","status":"ok","data":{"stored":32,"last_addr":"0xE7E7E7E7E7","last":"DEADBEEF"}}
View this module’s .ino source →
4.6 Lab transmitter +

A low-power test transmitter that sends to your own nRF24 node so you can check a link and measure range. It reports whether each transmission was acknowledged. This is explicitly a self-test to a node you own — not for injecting into other devices.

What the output means

ch
Channel used for the test transmission.
addr
The destination pipe address of your own receiving node.
sent
Count / marker that a test packet was transmitted.
ack
Whether the receiving node acknowledged the packet (ACK) or not (no ack) — your pass/fail for the link.

Example telemetry

{"module":"4.6","status":"ok","data":{"ch":76,"addr":"0x1Node","sent":1,"ack":true}}

07

Infrared · 38 kHz

Learn, decode, analyse and replay infrared remote signals on GPIO4 (RX) / GPIO5 (TX). Verify the LED with a phone camera. (Flashed, hardware testing in progress.)

7.1 38 kHz carrier modulation +

Drives a continuous 38 kHz, 50%-duty carrier on the IR LED (via the ESP32's LEDC hardware). 38 kHz is the frequency almost all consumer IR remotes use, so this is the baseline transmitter test. The light is invisible to your eye — point a phone camera at the LED and you'll see it glow.

What the output means

freq_hz
The carrier frequency being generated, in Hz (38000).
duty_pct
The duty cycle as a percentage (50) — how much of each cycle the LED is on.
pin
The GPIO driving the IR LED (GPIO5).

Example telemetry

{"module":"7.1","status":"ok","data":{"freq_hz":38000,"duty_pct":50,"pin":5}}
View this module’s .ino source →
7.2 IR pulse learning +

Captures the raw mark/space timing of every IR burst the receiver sees — i.e. the exact on/off durations that make up a remote's signal, with no attempt to interpret the protocol. This is the raw recording you can later replay with 7.3.

What the output means

count
How many timing values were captured for the burst.
overflow
YES if the capture buffer filled before the signal finished (the recording is truncated), otherwise no.
timings_us
The array of raw mark/space durations in microseconds — the alternating LED-on / LED-off lengths that encode the button press.

Example telemetry

{"module":"7.2","status":"ok","data":{"count":67,"overflow":false,"timings_us":[9000,4500,560,560,560,1690,560,...]}}
View this module’s .ino source →
7.3 IR signal replay +

Re-transmits the last signal captured by 7.2, 7.4 or 7.5 exactly once, then returns to idle. If the protocol was decoded it sends it properly; if the signal was only captured raw, it replays the raw timing at 38 kHz. This is how you prove a capture round-trips through the hardware.

What the output means

protocol
The protocol being replayed, when the source capture was decoded (e.g. NEC).
value
The code value being resent (hex), for a decoded signal.
bits
Bit length of a decoded signal — or, for a raw replay, count pulses is reported instead.
action
A marker that the one-shot resend fired before the module idles again.

Example telemetry

{"module":"7.3","status":"ok","data":{"protocol":"NEC","value":"0x20DF10EF","bits":32,"action":"replayed"}}
View this module’s .ino source →
7.4 IR protocol decode +

Listens on the IR receiver and decodes the signal into a named protocol and code value — NEC, Sony SIRC, RC5, RC6 and the other formats the IRremoteESP8266 library understands. This turns a button press into a clean, reusable code instead of raw timings.

What the output means

protocol
The decoded protocol name (e.g. NEC, SONY, RC5). Unrecognised signals come back as UNKNOWN.
value
The decoded command as a hex value — this is the unique code for the button that was pressed.
bits
How many bits the decoded code is (e.g. NEC is 32 bits) — a sanity check that the decode is complete.

Example telemetry

{"module":"7.4","status":"ok","data":{"protocol":"NEC","value":"0x20DF10EF","bits":32}}
View this module’s .ino source →
7.5 IR signal analysis +

Measures a captured burst: it sums all the mark (LED-on) time and all the space (LED-off) time and reports the totals plus the overall duty cycle. This characterises the shape of a signal — useful when a remote won't decode and you want to see what it's actually doing.

What the output means

protocol
Decoded protocol name if the library recognised the burst, else UNKNOWN.
mark_us
Total LED-on time across the burst, in microseconds.
space_us
Total LED-off time across the burst, in microseconds.
total_us
mark + space — the full length of the signal in microseconds.
duty_pct
mark as a percentage of total — the duty cycle of the whole burst.

Example telemetry

{"module":"7.5","status":"ok","data":{"protocol":"NEC","mark_us":22350,"space_us":45150,"total_us":67500,"duty_pct":33.1}}
View this module’s .ino source →
7.6 LED circuit test +

Fires a short 26 µs pulse on the IR LED every 10 ms — a steady, easy-to-scope heartbeat for checking the transmit driver circuit is wired and working, independent of any real signal. Again, a phone camera will show the LED flickering.

What the output means

pulses
A running count of pulses fired.
pulse_us
The width of each pulse in microseconds (26).
period_ms
How often a pulse fires, in milliseconds (10).
pin
The GPIO driving the IR LED (GPIO5).

Example telemetry

{"module":"7.6","status":"ok","data":{"pulses":418,"pulse_us":26,"period_ms":10,"pin":5}}
